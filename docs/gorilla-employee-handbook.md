# 大猩猩员工小册

本小册是大猩猩名称、能力、模式、故事与素材的维护索引。前端实际资料源位于 `durian-web/src/data/gorillas.ts`，新增员工时应优先更新该文件。当前共有 8 位在职员工。

## 在职员工

- 三果判官·米奇（`mitsuhiko`）：库存中时，所有包含 3 个水果的订单无效。（经典模式、猩风作浪）他吃过缺斤少两的亏，从此查账必数三遍，遇到一次报上三个水果的订单便当场作废。
- 悠哉掌柜·墨菲（`moo`）：没有特殊效果，但会作为普通大猩猩卡占据库存。（经典模式、猩风作浪）他总在柜台边慢慢喝茶，看似什么都没做，庞大的身影却足以让所有人重新掂量库存。
- 香蕉克星·汉娜（`nana`）：库存中时，所有香蕉订单无效。（经典模式、猩风作浪）她曾被倒塌的香蕉货箱困住一夜，从此见到香蕉订单就盖下红章退回。
- 葡萄珠匠·紫罗（`grape-beadsmith`）：每张仍有效的葡萄订单按 1 个葡萄计算。（猩风作浪）她只认可每串里最圆的一颗精品，因此再大的葡萄订单也只算一粒。
- 换位魔术师·莫比（`order-swap-magician`）：将每张水果库存卡草莓与葡萄半区的 `effectiveFruit` 对调，原卡内容与订单保持不变。（猩风作浪）他在闭店后练习货架魔术，响指一打便让草莓与葡萄库存悄悄换位。
- 封箱经理·克莱德（`boxing-manager`）：按未受莫比、巴鲁影响的 `baseInventory` 保护库存最少的整种水果，库存牌与该水果订单都封箱且即使库存为 0 也不触发爆单；并列按草莓→香蕉→葡萄→榴莲取第一项。（猩风作浪）他从装箱线升任经理，最擅长在混乱出货前锁定最稀缺的货箱；一旦封箱，最低库存品类便暂停追责。
- 库存搬运工·巴鲁（`inventory-mover`）：克莱德保护项不能作为来源；其余莫比处理后的有效库存中选最高来源，向当前最低项搬 2 颗；实例按整半区 2、从 3 取 2、两个 1 各取 1 的级别依次选择。（猩风作浪）他熟记每个货位的重量，总把最满货位的一车货搬去最空的货位，让仓库重新均衡。
- 临时主管·菲恩（`temporary-supervisor`）：每种水果按原订单顺序的第一张订单计 0，且该订单不再处理后续订单效果；同水果后续订单继续结算。（猩风作浪）她临时接班后同时接电话、翻订单板和盖章，忙乱中会漏登每种水果最先到达的一张订单。

## 结算顺序

猩风作浪必须与服务端现有实现保持以下固定顺序：

1. 菲恩按原 `orders` 顺序扫描，每种水果第一次出现的订单计 0 并立即锁定；该订单不再接受米奇、汉娜或紫罗效果，同水果后续订单仍继续进入后续步骤。
2. 米奇只处理尚未锁定且数量为 3 的订单，使其无效并锁定。
3. 汉娜只处理尚未锁定的香蕉订单，使其无效并锁定。
4. 紫罗只处理尚未锁定、仍有效且数量大于 1 的葡萄订单，将其折算为 1 并锁定。
5. 莫比建立库存半区有效账本：每张水果卡按输入库存槽顺序记录左、右半区，只交换草莓与葡萄的 `effectiveFruit`，不改原卡与订单。
6. 克莱德仍按 `baseInventory` 初始库存封箱，保护库存最低的整种水果；该水果库存与订单都显示封箱，即使库存为 0 也不触发爆单。
7. 巴鲁在莫比后的有效总量中排除克莱德保护项，再选最高合格来源；目标为当前库存最低项（不排除保护项），来源与目标相同则静默。

前四步共用订单实例锁：同一订单最多命中一个订单效果。`validOrders` 只排除被米奇或汉娜判无效的订单；菲恩计 0 与紫罗改 1 的订单仍然有效，订单总数以四步实际命中的订单集合计算，不做反向预判。

克莱德以及巴鲁的来源/目标水果并列时，统一按草莓（`strawberry`）→香蕉（`banana`）→葡萄（`grape`）→榴莲（`durian`）顺序取第一项。巴鲁的实例选择遵循严格级别，级内按输入库存槽顺序、同卡左半区后右半区稳定选择：

- 优先一个 `count=2` 半区整取 2（`2 → 0`）。
- 没有前项时，选一个 `count=3` 半区取 2（`3 → 1`）。
- 再没有前项时，选两个 `count=1` 半区各取 1（`1+1`），每个来源各生成一辆车。
- 不允许 `count=1` 与其他数量混搭；合格实例凑不足 2 时静默。
- 保护水果即使总量最高也跳过，由次高合格来源自动顶上；目标仍可为保护水果。
- 来源与目标相同（包括全部相等）时静默；每次结算最多搬一组 2。

爆单使用巴鲁最终搬运后的库存计算，但克莱德仍按初始库存选出的保护水果继续豁免爆单。最低库存并列时克莱德只保护固定顺序第一项；即使该项初始库存为 0 仍受保护，其他水果照常可能爆单。

结算视觉与规则语义一一对应：克莱德按罩落、盖合、锁环、锁扣、高光阶段完成约 1500ms 封箱并保留最终态；巴鲁按解释中的 `inventoryId/cardId/side` 从明确半区扣除 pip，`3 → 1` 只扣两颗，莫比来源按 `effectiveFruit` 显示。每个 source 生成一辆小车，同轨错峰驶到巴鲁所在库存槽旁，在金光中由来源交叉淡出为目标，约 3400ms 后保留扣除、目标与汇总；普通玩家、自己与公共库存 actor 均使用逻辑百分比座位坐标，不做 DOM 测量。active、committed 与 reduced-motion 都落到同一最终态，原 reveal 库存 payload 始终不改。

## 新员工接入清单

1. 按用户要求明确员工加入的模式，再在服务端 `durian-server/src/game/types.ts`、`deck.ts`、`modes.ts` 注册卡牌与所属模式。
2. 在 `durian-server/src/game/rules.ts` 实现能力，明确其在固定结算链中的位置，并为单独能力、组合效果与模式牌组补测试。
3. 在 `durian-web/src/data/gorillas.ts` 增加正式 ID、名称、称号、能力、合理故事、发布状态、加入批次、模式和素材路径。
4. 制作 `750x1000 RGB` 标准角色卡，并从定稿角色的精彩区域截取、提炼或重绘 `256x256 RGB` 表情；发布为 `gorilla-<id>.png` 与 `emote-<id>.png`。
5. 更新员工手册、卡池历史、资源清单、生成工作流、README 和其他受影响的本地文档。
6. 在职角色总数超过 7 位时，大厅须按房间生成随机角色顺序；角色足够覆盖玩家时，玩家之间不得重复。
7. 运行服务端测试/构建、前端生产构建与资源规格检查。

只有模式、能力、服务端规则、测试、标准卡片、表情、员工故事和本地文档都齐全的员工才能标记为 `published` 并加入实际牌组；概念角色不得只在前端占位。
